Initial release — optimise video uploads to WebM (VP9/Opus) in the background via Payload's Jobs Queue. The source file is always stored untouched; the upload response returns immediately with `status: 'queued'`, and a durable job (retries: 3, cron-safe, idempotent per preset) encodes one hidden sidecar document per configured preset in the same collection (same storage adapter), linked from the source via `renditions` rows and garbage-collected on file replacement and deletion. Out of the box every upload becomes the full `widthPresets()` ladder — 2560w down to 426w, ~1.5× apart — which costs less than a single uncapped encode of a 4K master (7.4 MP against 8.3) because encode cost tracks pixel count, and shrinks automatically for smaller sources. `resolutionPresets()` is the height-based equivalent if you think in `720p`; both take their per-rung CRF from Google's published VP9 table by pixel count, so a 9:16 crop 1080px wide is graded like the 1920×1080 rung it has exactly as many pixels as. `portrait: true` adds focal-point-framed 9:16 crops — the one shape mismatch worth its own encode, since `object-fit: cover` on a landscape master in a phone hero overdraws ~3× — and `quality: 'high' | 'balanced' | 'small'` shifts the whole ladder as a CRF offset rather than flattening it to one number. `encoding.audio: false` drops the audio stream for muted background video. Every rendition's dimensions are measured off the encoded file and stored on its row, so selection needs no extra query and no shipped component. `getVideoSourceSet(doc, { sizes })` takes an `<img sizes>`-style string and **solves** it: a slot width is affine in viewport width and the rungs are known, so each crossover falls out of the inequality instead of being sampled from author-chosen bands, and the emitted `min-width` thresholds land exactly where one rung stops being enough — including breakpoints no stylesheet mentions, like a `max-width` container's plateau. The grammar is deliberately narrow (`Npx`, `Nvw`, `calc(Avw ± Bpx)`), keeping the runtime a few regexes; it throws in development pointing at the tooling and falls back to the original file in production. `dpr` takes a list, defaulting to `[1, 2]`, with thresholds at the _midpoint_ between multipliers — `min-resolution` is a floor, so gating the 2× bucket at `2dppx` would strand every 1.5dppx device on the 1× rung — and a scalar still means one bucket with no resolution queries. A companion `aspect` string drives shape selection for slots that change shape. `pickVideoVariant(doc, { width, height, dpr })` remains for measured slots that re-evaluate on rotation, and the dependency-free `/frontend` subpath also provides `getVideoSources()` / `getRenditionUrl()` — renditions in preference order with the original as the guaranteed fallback. A separate `./sizes-devtools` entry generates the `sizes` string by measuring the real page: `fitSizes` recovers the piecewise formula from samples (splitting on slope change, and locating continuous joins at the intersection of the fitted lines, which is the only way to find them), `sweepSizes` drives any object with `evaluate`/`setViewportSize` so Playwright, Puppeteer or your own harness all work with no browser dependency added, `expectSizesAccurate` runs it in reverse as a CI gate that fails only when the difference changes which file is served, and a `payload-video-sizes` CLI prints a line to paste. The fit describes the layout only, never a ladder, so the string survives changing your presets. Helpers warn in development when `renditions` rows arrive unpopulated (which otherwise silently serves the original), when a document has nothing to choose between, and when `aspect` names a shape that was never encoded. Hosts control backgrounding via `dispatch` (Next `after`, `waitUntil`, `void run()`, an external queue, or `'inline'` to accept blocking deliberately); with none configured the job runs inline, or detached once the upload commits on databases with transactions, and the plugin warns at boot. Guardrails: `skipIfLarger` and `skipRedundantPresets` (both per preset, both recorded on the document so nothing is re-encoded twice), `maxInputFileSize`, `ffmpeg.maxConcurrent` (default 2), `ffmpeg.timeoutMs` per encode — which defaults to `jobs.maxRunMs` and to no limit at all when that is unset, since a per-encode cap only ever proxies the host's own execution limit and a fixed one throttled the worker deployment that exists to escape those limits — init-time validation, and a boot-time ffmpeg/encoder check. Source videos are never held in memory — ffmpeg reads them from disk and remote storage is streamed to a temp file. Conversions are guarded by a `renditionGeneration` counter and a merged final write, so a slow, duplicated or superseded run can never overwrite newer renditions, and renditions are only garbage-collected by writes that genuinely retire them (a new file, the job itself, or the regenerate endpoint) — never by an ordinary save, a restored version, or a duplicated document. Export `EXCLUDE_VIDEO_DERIVATIVES` for `filterOptions` on relationship/upload fields and for your own queries, since `baseListFilter` only covers the admin list view. A live admin sidebar panel (via `./client` and the import map) polls while the job runs and shows a condensed table of the stored renditions — file size and savings, open-in-new-tab, and per-preset or full regeneration, with presets the job decided not to store collapsed into a single footnote naming them and why — through a `POST /<taskSlug>/regenerate` endpoint gated by the collection's update access and rate-limited to one queued conversion per document; the underlying `videoConversion` group tracks status, original file info, encode duration, skip reasons, and last error through the API.
